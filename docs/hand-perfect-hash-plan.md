# 牌姿の双方向キー：仕様と実装計画

作成日: 2026-11-25

## 目的

牌譜から得た牌姿に、衝突せず復元可能な整数キーを割り当てる。将来は、
ユーザーが正規表現のような条件で検索した牌姿をキーに変換し、Parquetに保存した
大量の牌譜の解析結果を検索・集計する。検索構文、牌譜の取り込み、DBそのものの
実装はこの計画の対象外とする。

ここでいう「完全ハッシュ」は、対象とする牌姿の同一性に対する単射と、その逆変換を
意味する。暗号学的ハッシュではない。キーの値は隙間なく連続している必要はない。

## 決定した要件

### 対象と同一性

- 四人麻雀を対象とし、当初の利用先は天鳳の鳳凰卓の牌譜とする。
- 打牌後の13枚相当と打牌前の14枚相当の牌姿を扱う。チー・ポン後の打牌前も
  含む。配牌途中は対象外とし、槓宣言直後で嶺上牌取得前のような意思決定のない
  中間状態にキーを与えることは要求しない。
- キーはゲーム状態や意思決定の種類ではなく牌姿を表す。同じ牌姿は、判断の種類や
  牌譜が異なっても同じキーとする。リーチ、和了、鳴きなどの可能性、局面情報、
  ツモ牌の区別は必要に応じてキーとは別に保持・絞り込む。
- 他家の打牌に対する判断では、まだ手元や固定面子にないその牌はキーに含めない。
  チー・ポン実行後は、鳴いた牌を固定面子の一部として含める。
- 34牌種に正規化し、赤牌と通常牌、同じ牌種の物理的な個体、手牌内の並び順は
  区別しない。赤牌などを条件にする場合は別情報を使う。
- 槓は実際の4枚として扱う。手牌と固定面子を合わせた各牌種の枚数は4枚以下とする。

### 2種類のキー

両者は別のキー空間として扱い、Parquetでも別列にする。同じ整数値が両方に現れても
同じ対象を意味しない。

1. **牌集合キー（`TileCountsKey`）**：手牌と固定面子のすべての牌を合わせた34牌種の枚数を表す。
   手牌と固定面子の区別、鳴きの種類や鳴き元は忘れる。decodeの結果も牌種ごとの
   枚数であり、忘れた情報は復元できない。
2. **鳴き込みキー（`MeldAwareHandKey`）**：手牌の牌種ごとの枚数と、固定面子の組を表す。チーでは順子と
   他家から鳴いた牌を区別し、ポン・大明槓・加槓では牌種と鳴き元の相対位置を
   区別する。暗槓も区別し、加槓では元のポンの鳴き元を保持する。チーの鳴き元は
   四人麻雀では上家である。大明槓と加槓は別とし、固定面子がない牌姿も対象とする。

`TileCountsKey`は試案の実装で別型として定義されている。鳴き込みキーの実装名はまだ
`MeldedHandKey`である。まず牌集合キーを実装・証明し、その後に鳴き込みキーを扱う。
用語の詳細は[hand hash用語集](../mahjong-hand-hash/docs/GLOSSARY.md)を参照する。

固定面子の**鳴いた順序は両キーに含めない**。鳴き込みキーでは、固定面子を順序を
忘れた組として扱い、同じ情報を別順序で与えても同じキーにする。順序による検索が
必要な場合は、牌譜等の別情報で追加絞り込みする。鳴き込み牌姿から固定面子を
牌に展開して合算すれば、対応する牌集合キーを計算できる。

牌集合キーは、鳴きが違っても牌の集合が同じなら一致する。鳴き込みキーは、例えば
同じ`123m`のチーでも1mを鳴いた場合と3mを鳴いた場合、また同じ牌種の大明槓と
加槓を区別する。どちらのキーも赤牌や鳴き順は復元しない。

### 保存契約

- キーは非負の符号付き64ビット整数とし、Parquetの`INT64`に保存する。
- 保存済みの解析結果を後から検索するため、公開した符号化方式と各値は固定する。
  方式を変更する場合は版を区別し、データとクエリーで同じ版を使う。版の保存場所
  と具体的な列名はDB設計時に決定する。異なる版や異なるキー空間の値をそのまま
  比較してはならない。
- 予約値は設けない。初版の具体的な番号付けは試案であり、版の表現は未決定である。公開前に固定し、
  代表的な入出力例を互換性テストとして保存する。未決定の方式を既存DBの
  永続キーとして使わない。

## Coreの手元牌の命名と牌集合キーの入力

### 現状と命名の課題

Coreの[`MahjongDomain.Hand`](../mahjong-domain-core/MahjongDomain/Hand.lean)は
`counts : TileCounts`だけを持ち、固定面子を含まない手元牌の基底である。
`Hand`という名前から固定面子を含む牌姿全体を想像しやすく、範囲が伝わらない。
一方、シャンテン側の[`Shanten.Hand`](../mahjong-shanten-calculation/Shanten/Core.lean)
はこの型を継承し、固定面子の**数**を追加する。固定面子の内容まで含む型ではない。

Coreの`Hand`の意味を変えて固定面子を含めるのではなく、現在の「手元牌の部分」
という意味を明確にする改名を検討する。以下は候補であり、**まだ改名は決定していない**。

| 候補 | 利点 | 注意点 |
|---|---|---|
| `StandingPart` | 牌姿全体の一部分だと明示でき、既存のシャンテン側の`standing`という語とも合う。 | `Part`だけでは牌の集まりと分かりにくい。手元牌が`standing`で、暗槓を含む固定面子を除くことの定義が必要。 |
| `StandingTiles` | 手元にある牌を扱う名前として具体的で、既存の`standing`という語とも合う。 | 実体は牌の列ではなく牌種カウントであり、名前だけでは枚数表現だと分からない。 |
| `StandingHand` | 麻雀の手元牌を連想しやすく、現行の`Hand`からの移行も理解しやすい。 | `Hand`が残り、牌姿全体と混同される余地がある。 |
| `ConcealedTiles` | 非公開の手元牌という意図を読み取りやすい。 | 暗槓も非公開だが固定面子なので対象外であり、`concealed`では境界を誤解しやすい。 |

現時点では、牌姿全体とは別の部品であることと既存語彙の両立から
**`StandingPart`を推奨**する。採用する場合も、その定義は手元牌の
`TileCounts`であり、固定面子・総枚数・妥当性を型自体には含めない。
改名時にはCoreの公開API・用語集と、これを継承・参照するconsumerを整合させる。
牌姿全体を表す共有型は別途設計し、上記の候補名をそのまま流用しない。

### `TileCountsKey`のデータソース

`TileCountsKey`は、**合算済みの`TileCounts`を入力にする**。
キーが表すのは牌種ごとの枚数であり、手元牌か固定面子かを区別しないためである。
牌姿全体から作る場合は、手元牌と固定面子の牌を展開・合算し、その結果を渡す。
槓は4枚として合算する。変換後は元の区別や鳴き情報を復元できない。

ただし、任意の`TileCounts`が対象ではない。Coreの`TileCounts.Valid`による
各牌種4枚以下と、合計13〜18枚の両条件を満たすものを対象とする。合計枚数の条件は
Coreの`TileCounts.HasFullHandSize`に置き、`TileCountsKey`側で再利用する。これは合算後のカウントの
条件であり、手元牌の部品に常に13〜18枚を要求するものではない。また、これらの
条件だけでは固定面子の構成可能性や牌譜上の到達可能性を証明しない。

encodeは対象のすべての`TileCounts`で成功し、decodeは同じ枚数ベクトルを返す。
型として`TileCounts`を使うことと、任意の`TileCounts`を符号化できることは異なる。
たとえば総枚数が0枚の`TileCounts`はCoreの4枚上限を満たすが、キーの対象外である。
既存の試案には枚数ベクトルのrank/unrankがあるため、再利用を検討する。ただし、
全域の正しさは改めて証明する必要がある。

## 実装の前提と検証すべき範囲

手牌の枚数を`h`、固定面子の個数を`m`、そのうち槓の個数を`k`とすると、対象の
構造上の条件は`0 ≤ k ≤ m ≤ 4`、`h + 3m = 13`または`14`である。実際に占有する
牌数は`h + 3m + k`、すなわち`13 + k`または`14 + k`となる。全体の牌数は
13〜18枚になり得るが、枚数がその範囲にあるだけでは有効な固定面子を構成できる
とは限らない。

構造的に妥当な牌姿と、ある特定の牌譜・ルールで実際に到達可能な局面は別概念で
ある。ハッシュの入力仕様に牌譜の履歴を要求せず、鳴きの形・鳴き元・枚数・
牌種の上限を検査する方針とする。天鳳の牌譜からどの地点を抽出できるかは、
将来の取り込み処理で別途検証する。

牌集合キーの計算は固定面子を忘れるため、13〜18枚かつ各牌種4枚以下の
枚数ベクトルを計算上の定義域とする案を採る。この集合には、対象の実際の牌姿から
得られないベクトルも含み得る。decodeの成功を牌譜としての到達可能性の証明と
みなさず、実際の牌姿を入力する境界では元の情報に対して検証する。範囲外のキーや
不正な入力の扱いは明示的な失敗とする。

## 64ビットへの収まり

現時点のモデルでは、仕様を削らず非負の`INT64`に収まる見込みがある。以下は
候補数の上界であり、実装の出力範囲の証明ではない。

`C(n)`を、34牌種それぞれ0〜4枚で合計`n`枚の枚数ベクトルの数とする。これは
`(1 + x + x² + x³ + x⁴)³⁴`の`xⁿ`の係数である。

- 牌集合キーの候補数 `Σ C(n)`（`13 ≤ n ≤ 18`）は
  **37,916,986,367,500**、46ビットで表せる。
- 鳴き込みキーでは、固定面子1個の候補を高々403通りと数える。
  チーは21順子×鳴き牌3通り、ポン・大明槓・加槓は各34牌種×鳴き元3通り、
  暗槓は34牌種である。
- 順序を忘れた`m`個の固定面子に重複も許す上界は`binom(402 + m, m)`。
  手牌と固定面子の牌種重複を検査しない粗い上界は
  `Σ[m=0..4] binom(402+m,m) × (C(13-3m) + C(14-3m))`
  = **20,454,710,139,075**、45ビットである。

どちらも`2^63`未満である。後者は不正な牌の重複なども含むため実際の対象数では
ない。この上界は鳴き順、赤牌、局面情報等をキーに含めない前提に依存する。
実装時には計算式、各範囲、整数オーバーフローがないことを検証する。

## 実装方針

1. **ドメインとAPIを定義する。** Coreの
   [`TileCounts`、`Tile.index`、`copiesPerTile`](../mahjong-domain-core/MahjongDomain/Tile.lean)
   を利用し、枚数ベクトルと固定面子の情報・妥当性・順序を忘れた同一性を定義する。
   既存の[`Hand`](../mahjong-domain-core/MahjongDomain/Hand.lean)は手牌の枚数のみ、
   [`Shanten.Capacity.FixedMeld`](../mahjong-shanten-calculation/Shanten/Capacity/Basic.lean)
   は面子や槓の牌を表すが鳴き元・鳴き牌・槓の種類までは保持しない。そのままでは
   鳴き込みキーに必要な情報を復元できない。共有の牌姿概念はCoreに置き、検索や
   牌譜処理はconsumer側に置く。既存の型との変換では失われる情報を明示する。
2. **番号付けを設計・固定する。** 牌種順には既存の`Tile.index`を使う。候補として、
   枚数制限付きベクトルを枚数別にrank/unrankし、鳴き込み側は固定面子の正規順の
   組と手牌を組み合わせる。固定面子数と13・14枚相当ごとに重ならない区間を設け、
   上界で示した候補空間を使える。不正な固定面子と手牌の組に対応する穴は
   decodeで拒否する。実際の順序、区間の開始値、固定面子の番号と版を仕様として
   文書化してから公開する。
3. **Leanで双方向と正しさを実装する。** 各キー空間で、有効な入力をencodeして
   decodeすると元の同一性に戻ること、encodeが単射であること、decodeに成功した
   キーを再encodeすると同じキーになることを証明する。鳴き込みから牌集合への射影
   と両キーの関係も検証する。範囲外、予約値、不正な候補の穴、無効な牌姿は明示的に
   失敗させる。Leanのモジュール方式は[基本方針](./lean-module-policy.md)に従う。
4. **実行可能な利用先へ移植する。** Leanの仕様・固定例を正本として、必要になった
   言語に移植し、同じ入力に同じ数値を返すことを共通テストで確認する。Parquetへの
   格納と版の照合は、それを利用するDB側の別作業とする。

## 初版番号付け（検証中の試案）

[`MahjongHandHash.HandKey`](../mahjong-hand-hash/MahjongHandHash/HandKey.lean)が
試案を実装する。鳴き込みキーの往復・単射・出力範囲の全域証明と十分なテストは未完了であり、
番号付けは公開・固定済みではない。永続キーとして使用しない。版番号をキーに
埋め込まず、保存列・データセットの外で版を管理する方針とする。異なる版や
異なるキー空間の値を比較しない。

修正前の試案には複数固定面子の組rankに衝突があった。例えば、同じ手牌
`456789m1p`に対し、`123m`の2mを鳴いたチー2組と、`123m`の1mを鳴いた
チー1組・中の暗槓1組は、いずれもキー`4244394020351`となる。以下は設計意図で
ある。この衝突はrank/unrankのブロック数を一致させて修正し、両入力のキーが異なる
回帰テストを追加した。ただし、全域のLean定理は未証明であり、以下の契約を形式証明したことを意味しない。
公開encode/decode APIはINT64範囲と個々の呼び出しの往復一致を実行時に検証し、
検査に通った場合だけ成功を返す。これは未検査の値を通さないためのガードであり、
番号付け全域の形式証明や版固定とは区別する。

- 牌集合キーはLeanの`Int`値を持つ別型で表し、非負の符号付き64ビット範囲のみ有効とする。
  総枚数を13、14、15、16、17、18の順に区間を置く。各区間内は`Tile.index`
  昇順で、各牌種の枚数を0〜4として左から辞書順（最初の牌種が最上位桁）に
  rankする。区間の開始値は前区間の候補数を加えたものとする。
- 鳴き込みキーは固定面子数`m = 0..4`ごとに、手牌枚数13-3mの区間を先、続いて
  14-3mの区間を置く。区間内は固定面子の組rankを上位、手牌枚数rankを下位として
  `fixedRank * C(handTotal) + handRank`で番号付けする。
- 固定面子の番号は403通りを連続番号0..402で表し、チー63、ポン・大明槓・加槓は
  各102、暗槓34の順で配置する。チー内はスート順（man/pin/sou）、開始ランク、
  鳴き牌の位置（left/middle/right）で番号付けする。
- ポン、大明槓、加槓内は牌種`Tile.index`、鳴き元の相対位置
  （下家/対面/上家）の順で番号付けする。暗槓内は牌種`Tile.index`順とする。
- 固定面子の鳴き順は忘れ、`FixedMeld.index`昇順で重複を許す組として組rankする。
- 牌集合キー候補数は37,916,986,367,500、鳴き込みキー候補上限は
  20,454,710,139,075であり、いずれも`9223372036854775808`未満である。

## 全域形式証明に向けた仕様決定事項

この節の「全域」は、決めた有効入力すべてと、decodeが成功するキーすべてを対象に
するという意味である。有限個の例の列挙や、実行時にencode結果をdecodeして確かめる
ガードは、定理の代わりにはならない。形式証明をゴールとし、以下の推奨案を採る。

目標とする定理は、少なくとも次の4つである。

1. 有効な入力は必ずencodeに成功し、出力キーは`0 ≤ key ≤ 2^63 - 1`を満たす。
2. 有効な牌姿をencodeしてdecodeすると、定義した同一性の意味で元の牌姿に戻る。
3. decodeが成功したキーをencodeすると、同じキーになる。
4. したがって、同一性の異なる有効入力が同じキーを持つことはない（単射）。

encode/decodeは内部計算を`Nat`で行い、範囲の定理を得た後にのみ非負`Int`へ変換する。
`Except`は無効な入力や画像外キーを報告するために使い、妥当な入力に対する
`roundTripFailure`のような実装不整合エラーをAPI上の通常の結果として許さない。

### 決定が必要な事項と案

#### 1. 牌姿の定義域：2案

- **案A — 構造的に妥当な牌姿（推奨）:** 合計枚数、固定面子の形、鳴き元、
   手牌と固定面子を合わせた牌種ごとの4枚上限などを満たすものを対象にする。
   牌譜上で実際に到達可能かどうかは要求しない。ルール履歴を必要とせず、
   encode/decodeの定義域が有限データとして明確になる。
- **案B — 特定ルールで到達可能な牌姿のみ:** 牌譜の順序や局面履歴も条件に含める。
   実際の局面に絞れる一方、牌姿だけでは妥当性を判定できず、ハッシュ仕様が
   牌譜抽出・ルール解釈に依存する。

現行計画の方針どおり案Aを推奨する。牌集合キーについては固定面子を忘れるため、
13〜18枚かつ各牌種4枚以下のベクトルを定義域とし、鳴き込み可能な牌姿から
生成できることまでは要求しない。

#### 2. 妥当な入力のencode成功条件：2案

- **案A — 全妥当入力で必ず成功（推奨）:** 有効性を満たす入力なら、必ずキーを
   返し、範囲と往復性を定理で証明する。符号化関数の契約が明快で、呼び出し側が
   有効入力を渡した後の失敗を処理する必要がない。
- **案B — 妥当入力でも実行時検査で失敗し得る:** 現行の`roundTripFailure`のように、
   内部decodeとの一致を確認できた呼び出しだけ成功させる。未検証の結果を防げるが、
   「すべての妥当入力を符号化できる」という契約は保証せず、形式証明の代わりにも
   ならない。

本ゴールでは案Aを採る。実行時ガードは開発中の診断や防御として残す場合も、
定理を置き換えるものとは扱わない。

#### 3. 鳴き込み牌姿の同一性：2案

- **案A — 固定面子を順序なしの多重集合として扱う（推奨）:** 鳴いた順序は無視し、
   同じ固定面子が複数ある場合も多重度を保持する。現在の計画とrank方式に一致し、
   鳴き順を持たない牌姿キーとして扱いやすい。
- **案B — 固定面子の列として順序を保持する:** 鳴き順も異なる牌姿として符号化する。
   鳴き順検索には便利だが、候補数が増え、現在のキーとは互換でなくなる。

案Aを推奨する。重複面子は重複を許す多重集合として定義し、同じ構造を許すかどうかは
牌種ごとの物理枚数上限など、既に定めた有効性条件で決める。鳴き順が必要な用途では
キーとは別に保持する。

#### 4. decodeが受理するキー：2案

- **案A — 実際に有効な入力のencode像だけを受理（推奨）:** 負値、INT64範囲外、
   未使用区間、または復号結果が有効な牌姿でない「穴」は失敗にする。キーから
   有効な牌姿が得られれば、再encodeで同じキーになることを証明する。
- **案B — 上界内の全整数を何らかの値へ割り当てる:** 穴にも値を与えるため、
   decodeは全域関数にできる。一方、無効な牌姿や予約値まで意味付けが必要になり、
   将来の番号変更や予約値追加を難しくする。

案Aを推奨する。`keyMax`は割り当てた符号空間のexclusive上限と定義し、
一般には`0 ≤ key < keyMax`であってもdecodeが必ず成功するとはしない。decode成功の
必要十分条件は、そのキーが有効入力のencode像に属することとする。ただし牌集合キーの
現行番号付けについては、区間内に穴がなく、`0 ≤ key < keyMax`がdecode成功の必要十分
条件であることを証明済みである。予約値は設けない。

##### Leanのエラー処理に関するメモ

decoderの公開APIは、利用先での検証・診断方法が未定のため決めていない。
現在の`TileCountsKey.decode`は`Except TileCountsKeyError TileCounts`を返す試案であり、
範囲外キーは`keyOutOfRange`になることを証明済みである。

Leanで検討できる表現には、次のようなものがある。

- **`Option α`:** 成功値か`none`を返す。値の不存在だけを表せるが、失敗理由は持たない。
- **`Except Error α`:** 成功値か型付きのエラーを返す。理由を区別できるが、
  エラーの分類と利用側での扱いを決める必要がある。
- **前提の証明を引数にする:** 有効性を証明した入力に限り、失敗のない結果を返す。
  呼び出し側で前提を示す必要がある。
- **有効性を持つ型を使う:** 値と有効性の証明をまとめ、検証済みの値に対する
  操作を失敗しない形にできる。外部値を受け取る境界では別途検証が必要になる。
- **`IO`の例外:** ファイル操作など外部環境とのやり取りに伴う失敗を扱える。
  純粋な符号化・復号処理とは区別する。

`Option`と`Except`はともに`do`記法で失敗を伝播できる。`Except.toOption`はすべての
エラーを`none`に変換して理由を失うため、利用する場合は内部不整合を通常の範囲外と
区別する必要がないか検討する。`panic!`や`!`付きの操作もあるが、回復可能な失敗の
通常処理とは区別する。これらの記述は選択肢のメモであり、APIの採用方針ではない。

参考: [Lean公式: 添字と証明](https://lean-lang.org/functional_programming_in_lean/Interlude___-Propositions___-Proofs___-and-Indexing/)、
[OptionとExcept](https://lean-lang.org/functional_programming_in_lean/Monad-Transformers/A-Monad-Construction-Kit/)、
[Except API](https://lean-lang.org/doc/api/Init/Control/Except.html)。

#### 5. 番号付けの方式：2案

- **案A — 現行の枚数別rankと固定面子組rankを固定（推奨）:** 牌種順、
   digitの辞書順、区間順、固定面子index、重複を許す昇順組rankをすべて仕様化する。
   候補空間が小さくINT64内に収まる見積りがある一方、rank/unrankの正しさを
   部品ごとに証明する必要がある。
- **案B — 単純な混合基数・直積符号化へ変更:** 部品ごとの証明は単純になる場合があるが、
   未使用組合せを多く含むためキー範囲が大きくなり、INT64内に収まるか再計算が必要。
   既存のテストベクトルとも互換でなくなる。

案Aを推奨する。既存の番号付けを変更する場合は別バージョンとし、既存キーとの
互換性を暗黙に保つことは要求しない。

#### 6. キー型と整数表現：2案

- **案A — 空間ごとの別型、内部rankは`Nat`（推奨）:** `TileCountsKey`と
   `MeldAwareHandKey`を混同できない型にし、非負性・範囲を証明した後で保存用`Int64`へ
   変換する。誤ったキー空間へのdecode呼び出しを型で防げる。
- **案B — 両方を`Int`の別名として扱う:** 実装と変換は簡潔だが、負値や範囲外値が
   入り得るうえ、異なるキー空間をLeanの型検査が区別しない。

案Aを推奨する。各キー空間の意味上の定理は独立して証明し、シリアライズ時の
`Int64`変換には非負・上限の証明を要求する。

### 推奨案で証明する補題の順序

上記の仕様を固定した後、次の部品定理を積み上げる。

1. `countDigitsExactly`が、残り牌種で指定枚数を作るベクトル数と一致する。
   この定理の範囲は牌種数34以下、指定枚数18以下に限定する。
2. `vectorRank`が有効ベクトルの範囲内にあり、`vectorDigitsUnrank`と互いに逆である。
3. `FixedMeld.index`と`FixedMeld.ofIndex`が有効な固定面子で互いに逆である。
4. `fixedComboCount`が、403種類から重複を許して選ぶ昇順の組数と一致し、
    `fixedComboRank`と`fixedComboUnrank`が正規化済みの組で互いに逆である。
5. 各区間が重ならず、区間offsetと各rankを組み合わせたキーが`keyMax`未満である。
6. decodeが返す牌姿の有効性と、encode/decodeの両方向の往復性を証明する。
7. 牌集合キー・鳴き込みキーそれぞれの上限が`2^63`以下であることを示し、
    最後に符号付きINT64への変換が安全であることを証明する。

この分解では、各補題の前提に有効性条件と同一性の定義を明示する。有限個の固定例は
番号付けの互換性を守る回帰テストとして併用するが、上記の定理の代替にはしない。

牌集合キーについて、候補数の定理は上記の有限範囲でLeanにより証明済みである。
長さと合計を満たし各要素が0〜4の列を重複なく列挙し、その長さが候補数と一致する。
また、合計18枚以下についてrankの範囲とrank/unrankの両方向の逆変換を証明した。
候補列の数とrankの単射性から、各区間内のすべてのrankに有効なベクトルが存在すると
示している。これを枚数別の区間と結び付け、各牌種4枚以下・合計13〜18枚のすべての
入力でencodeが成功し、元のベクトルに戻ることと、単射性・INT64範囲を証明済みである。
decodeが成功するのは`0 ≤ key < keyMax`の場合に限り、成功時には有効なベクトルを
返し、再encodeで同じキーになることも証明済みである。`keyMax`は
37,916,986,367,500であり、この区間に穴や予約値はない。

これらの証明は牌集合キーについてのものである。鳴き込みキーの全域証明と、
永続キーとしての番号付けの版固定は引き続き必要である。

## 受け入れ条件・検証

- 有効な各入力でencodeが成功し、出力が`0 ≤ key ≤ 2^63 - 1`を満たすこと、
   両方向の往復、encodeの単射性をLeanで証明する。実行時検査や有限範囲の
   列挙テストだけを全域定理の代わりにしない。
- 13・14枚相当、チー・ポン直後、暗槓・大明槓・加槓、複数の固定面子と槓、
  牌種ごとの4枚上限、13〜18枚の境界を含む代表例を用意する。
- 同一性の例として、手牌順・赤牌・鳴き順の違いは一致させる。一方、チーの鳴き牌、
  ポン等の鳴き元、大明槓と加槓は鳴き込みキーで区別する。牌集合キーではそれらを
  区別せず、4枚の槓を落とさない。
- 負値・範囲外・穴のキー、5枚以上の牌種、固定面子を含めた枚数超過、不正な
  順子・鳴き元、固定面子5個以上、13・14枚相当でない鳴き込み入力を拒否する。
  牌集合decodeの成功だけから実際の牌譜に現れると判定しない。
- 固定版のテストベクトルを複数言語間で共有し、保存済みの値との互換性を確認する。
  将来の牌譜取り込みでは、実牌譜の抽出結果とキーの結合を別途検証する。
- 検索対象の規模、encode/decodeの呼び出し回数、Parquetのキー検索方式が決まった
  段階で、代表データによる速度とメモリを測る。具体的な性能目標は未決定であり、
  現時点では満たしたと主張しない。
