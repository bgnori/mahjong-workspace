# HandSnapshot設計レビュー

レビュー日: 2026-11-26

対象: Core `f647dc8`、hand-hash `9571c12`、シャンテン `747352f`

関連: [共有牌姿表現の設計](./shared-hand-representation-design.md)、
[牌姿キーの計画](./hand-perfect-hash-plan.md)

## 結論

`HandSnapshot`は、**四人麻雀の正規化済み牌姿を共有し、検索や計算の入力とする型**
として妥当である。手元と固定面子を分け、暗槓を固定面子として4枚占有させ、
鳴きの違いを保持する設計は目的に合う。一方、これは**プレイヤーの意思決定時の
局面全体でも、牌譜の可逆表現でもない**。赤牌、ツモ牌の区別、捨て牌、立直、
手番、直前の行為などを別に保存しないDBでは、打牌・鳴き・和了の意思決定を
正しく再現・集計できない。

直ちに型を局面全体に拡張するより、Coreの共有牌姿と、牌譜・ルールに依存する
イベント／判断機会の層を分離することを推奨する。以下の提案はレビューであり、
現行コードが保証する性質や実装済みのDB仕様ではない。

## 現状の契約と評価

[`HandSnapshot`](../mahjong-domain-core/MahjongDomain/HandSnapshot.lean#L28)は
`standing : TileCounts`と`fixedMelds : List FixedMeld`を持つ。
[`Tile`](../mahjong-domain-core/MahjongDomain/Tile.lean#L41)は赤5を通常の5と
同じ34牌種に正規化し、`TileCounts`は`Tile → Nat`である。固定面子はチー、
ポン、大明槓、加槓、暗槓に分かれ、チーの鳴き牌位置、その他の明副露の
鳴き元を保持する。加槓の鳴き元は元のポンのものという意味である
（[既存設計](./shared-hand-representation-design.md#共有牌姿の構成)）。

[`occupiedCounts`](../mahjong-domain-core/MahjongDomain/HandSnapshot.lean#L33)は
手元と全固定面子を合算する。槓は1面子だが4枚を占有する。構築時に妥当性は
検査されない。シャンテンへの
[射影](../mahjong-shanten-calculation/Shanten/Capacity/HandSnapshot.lean#L10)は
鳴き詳細を捨てて占有牌と面子数を渡し、妥当性検査は利用側に残す。

**良い点**

- `Shuntsu`と`Fin 3`により、字牌のチー、範囲外の順子開始位置や鳴き位置を
  固定面子単体で表せない。暗槓と明副露を区別でき、門前判定に必要な面子の
  情報も保持する。ただし門前かつ立直済みかなどは別の情報である。
- 手元だけの`Hand`と牌姿全体を区別し、同じ形の重複チーを保持する。
  全占有牌への射影と、固定面子の形を使う計算の両方に使える。
- 正規化牌姿の同一性は解析目的に明快で、異なる鳴き牌・鳴き元や
  大明槓／加槓を区別できる。これらを不要とする計算には別途射影できる。

## 指摘と推奨

### 高: 意思決定を牌姿キーだけで識別しない

同じ`HandSnapshot`でも、ツモ直後の打牌判断と他家の打牌への鳴き・ロン判断では
選択肢が異なる。同じ14枚相当の手元でも、どの牌をツモったかが違えば
ツモ切り／手出しが異なり得る。5を捨てる場合も赤5か通常5かで選択と価値が
異なるが、`standing`はその違いを持たない。固定面子内の赤牌、物理牌のID、
鳴いた時点・順序も復元できない。鳴き元が同じでも、牌譜上のどの捨て牌を
鳴いたかは特定できない。

したがって`HandSnapshot`を**正規化された検索・集計軸**として保持し、
判断レコードには少なくとも判断主体、時点、判断種別、直前イベント、
実際の行為、赤牌とツモ牌の区別を持つ詳細状態またはそれを復元できる参照を
設ける。上家・対面・下家の基準は鳴いたプレイヤーからの相対位置として
交換契約に明記する。牌譜形式固有IDは入力境界に留め、元データ側には
形式とともに保存する。局所的な赤牌属性だけでよい利用と、牌譜照合に物理IDが
必要な利用を区別し、IDのない入力に推測したIDを付けない。

具体例: 手元に通常5mと赤5mがあり5mを打った場合、正規化前の2つの選択肢は
同じ`Tile`に潰れる。また同じ鳴き後牌姿でも、それがチー直後の打牌か、
後のツモ直後かによって、ツモ切り情報や、ルールによっては食い替え制限が
異なる。牌姿だけの集計は有用だが、その結果を赤牌選択や合法手の集計と
解釈してはいけない。

### 高: 構造妥当性、局面の合法性、牌譜到達可能性を分ける

型自体は固定面子5個、同一牌種5枚、任意の手元枚数を表現できる。
これは不完全データや途中状態にも使える反面、構築成功は有効性を意味しない。
hand-hashの[`valid`](../mahjong-hand-hash/MahjongHandHash/HandKey.lean#L324)は
対象を固定面子数`m ≤ 4`、`standing.total + 3m = 13`または`14`、
全占有牌の各牌種4枚以下に限定している。これはCoreの構築時保証ではない。
`TileCounts.HasFullHandSize`の13〜18枚という範囲だけでも、固定面子との
対応や到達可能性は分からない。

推奨する検証境界は次のとおり。

1. **構造**: 固定面子数、全占有牌の4枚上限、対象段階に応じた枚数。
   13／14枚相当は通常の安定した手牌状態に対する条件であり、配牌途中や
   イベント処理の中間状態すべてに無条件で課さない。
2. **局面とルール**: 自分の手番、対象の捨て牌、チーの鳴き元、立直後の槓、
   食い替え、振聴、王牌や流局条件などを、適用ルールと履歴に照らして判定する。
   自分の占有枚数だけでは、他家の見えている牌を含む整合性も保証できない。
3. **到達可能性**: 牌譜の順に状態遷移を再生し、行為・所有・移動・得点等を
   検証する。構造的に有効な牌姿のdecodeは、この証明ではない。

槓は遷移として特に注意する。加槓はポンを追加の面子として数えず置き換える。
搶槓の判断窓では加槓を確定した状態と宣言中の状態を混同せず、嶺上牌取得前後や
槓ドラ公開のタイミングも対象ルール・牌譜仕様に従う。たとえば
[日本プロ麻雀協会競技規定](https://npm2001.com/about/regulations/)はチー、
加槓と搶槓を規定しているが、すべてのルールセットに同一の詳細を仮定しない。
三人麻雀、抜きドラ、赤牌の枚数などは別のルール契約が必要で、現行の四人・
34種・各4枚という前提だけで汎用的に検証できると主張しない。

### 中: Leanの等号と意図した同一性を明確にする

現行の[`Equivalent`](../mahjong-domain-core/MahjongDomain/HandSnapshot.lean#L47)は
手元カウントの関数等号と固定面子リストの`Perm`で定義され、
[`same`](../mahjong-domain-core/MahjongDomain/HandSnapshot.lean#L51)は全牌種と
`Perm`を計算で比較する。固定面子の順序を無視するのはこれらであり、
Leanの構造体の通常の`=`ではない。例えば`[a, b]`と`[b, a]`は`a ≠ b`なら
`Equivalent`だが構造体等号では異なる。`TileCounts`は関数なので、構造体の
機械的な等値比較や永続化可能な配列だと考えてはいけない。

設計を変える前に、公開APIに次の定理を追加することを推奨する。
現行Coreの`HandSnapshot`モジュールにはこれらの定理はまだない。

- `Equivalent`の反射律・対称律・推移律、および`same a b = true ↔ Equivalent a b`。
  後者には`Tile.all`の網羅性を使う。
- `Equivalent`なら`occupiedCounts`が等しいこと、固定面子の個数と各種の
  多重度が保たれること。逆は一般に成り立たない。
- 必要に応じて`Setoid HandSnapshot`を提供し、同値関係を使うAPIを明示する。
  `Setoid`だけでは通常の`=`は変わらない。商型や正規化済み構造体を採るかは、
  計算・シリアライズ・下流の互換性を確認して別途決める。

固定面子の`BEq`は`DecidableEq`から定義されるが、その法則のインスタンスが
公開されているとは限らない。下流の証明で必要なら`LawfulBEq`の有無と法則を
確認する。面子列の順序を捨てることは牌姿の抽象化として合理的だが、
イベント順序を復元する用途には使えない。

### 中: 比較・キー・交換の契約を別々に固定する

`Equivalent`は牌姿の意味的同一性、hand-hashのキーはそのための符号化、
交換形式は別の契約である。[hand-hash実装](../mahjong-hand-hash/MahjongHandHash/HandKey.lean#L363)
は固定面子を番号でソートし、encode時にdecodeして`same`を確認する。
[テスト](../mahjong-hand-hash/MahjongHandHashTests/HandKey.lean#L145)には
403種類の固定面子例、順序交換、容量超過などがあるが、例や実行時検査だけで
全有効入力のencode成功・往復・単射が証明されたわけではない。

DBでは、安定した交換形式（34牌種の順、面子種・鳴き位置・方向、多重度、
未知値や不正値の扱い）を定義し、同値な入力の固定面子順を正規化する。
交換形式の版、キー空間の種類、キー番号付けの版を保存し、変更時の移行を
用意する。現状のキーを版固定・全域検証済みとみなさず、元の詳細データを
保持する。牌集合キーは手元と面子の区別まで失うため、鳴き込みキーや
判断レコードの代替にはならない。

## 牌譜DBの境界案

以下は最小限の論理モデルであり、テーブルの分割や実装言語を指定するものではない。

| 層 | 保持するもの | 用途と注意 |
|---|---|---|
| 原本・来歴 | 牌譜原本または再取得可能な参照、提供元・形式・形式版、取込版、対象ルール、対局／局の識別子 | 再処理と不整合調査。提供条件・利用権限も確認する |
| イベント | 局内の安定した順序、主体、ツモ・打牌・鳴き・槓・立直・和了等の種別と元データの牌情報 | 牌の移動と履歴を再生する。加槓と元ポン、鳴きと対象打牌を関連付ける |
| 判断機会 | 局とイベント位置、判断主体、判断種別、観測可能な情報、実際の選択、選択肢や合法性の導出元・版 | 複数プレイヤーに同時に機会があり得る。行為だけでなく不作為の意味も区別する |
| 派生表現 | 対象時点・主体に紐づく`HandSnapshot`、必要な詳細牌姿、計算結果、交換形式／キー／計算の版 | 量の多い検索・集計を高速化するキャッシュ。原本からの再導出可能性を保つ |

イベント位置は**判断前**か**判断後**かを明示する。例えば打牌判断はツモ後・
打牌前、鳴き判断は他家打牌後・応答確定前とし、結果のイベントへ参照を張る。
各判断の識別子は牌姿キーではなく、対局・局・順序位置・主体・判断種別などに
基づく。順序は同じ巡目だけでは足りない。牌譜の修正・重複取込に対する識別と
原本版の扱いも決める。

牌譜に現れない「見送り」は、**合法な機会が実際にあり、観測可能で、
その応答が記録または推論できる場合に限って**導出する。優先順位によって他家の
宣言が隠れた場合、牌譜が応答を記録しない場合、複数ロンや頭ハネの扱いなどでは、
沈黙を「選択可能だったが見送った」と断定しない。未観測・不明・非該当と
実際の見送りを区別し、導出根拠とルール版を保存する。

分析時はプレイヤーが**その時点で知り得た情報**と、牌譜の後から判明した他家の
手牌・山・結果を分離する。後者を判断時の特徴量に混ぜると情報漏洩になる。
観測できない他家の手牌は空手や0枚ではなく未知として扱う。記録欠落と
ルール上存在しない情報も区別する。点数、場風・自風、ドラ表示、捨て牌、
公開副露、立直、残り巡目、既知の振聴に関係する履歴などは目的に応じて必要で、
判定に十分な履歴がなければ合法性を不明として扱う。

## 推奨する検証例と優先順位

1. **同値性の証明**: 順序交換で`Equivalent`と`same`が一致、重複個数が違えば
   非同値、同値なら占有カウントが一致。異なる鳴き詳細が同じ占有カウントに
   射影される反例も用意する。
2. **ルール境界**: チーの3位置、ポンの3方向、暗槓・大明槓・加槓、加槓による
   置換、手元と固定面子を合わせた5枚目の拒否、13／14枚相当を検証する。
   加槓宣言・搶槓窓・嶺上牌取得を別時点としてテストする。
3. **判断DB**: 同じ正規化牌姿で赤5／通常5の選択、ツモ切り／手出し、
   異なる判断種別・公開情報を区別する。実際の見送りと未観測の区別、
   後から判明した情報を判断時点に混ぜないこと、局内順序の再生も検査する。
4. **交換・キー**: 固定面子の並べ替えと重複を含む共通例を言語間で往復し、
   不正入力は明示的に拒否する。キーの全域往復・単射・有効入力の成功、
   版固定および旧版からの移行は別途完了させる。

まず1と判断データの境界を明文化し、その後にCoreの証明、牌譜アダプターと
ルール別検証、DB実装を進める。現段階でこの文書はコード変更や新たな証明、
実牌譜を用いた再生テストの完了を意味しない。
