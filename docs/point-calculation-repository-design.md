# 点数計算レポジトリの設計案

作成日: 2026-11-28

関連: [共有牌姿表現の設計](./shared-hand-representation-design.md)、
[HandSnapshotの段階設計](./hand-snapshot-phase-design.md)、
[Leanモジュール方針](./lean-module-policy.md)

## 目的と位置付け

Coreの`HandSnapshot`を入力として、和了手の役・符・翻・点数と支払いを計算する
独立したconsumerレポジトリを追加する。本書は実装前の設計案であり、レポジトリの
作成、採用ルールの最終決定、計算APIの確定を意味しない。

Coreは牌姿の共有語彙とその意味を定義し、点数計算レポジトリは役判定・符計算・
点数表・支払いなどの利用方法を定義する。点数計算固有の型や役定義をCoreへ
重複して追加せず、Coreの共有型を直接利用する。候補のレポジトリ名は
`mahjong-point-calculation`とする。

初期対象は日本式リーチ麻雀の四人打ちとする。ただし、複数のルール差が点数に影響する
ため、ルールを暗黙のグローバル定数にせず、明示的なルール設定として扱う。採用する
標準ルールと差分設定の一覧は実装開始前に確定する。CoreがLeanであるため初期実装も
Leanを想定し、Coreの型を直接importする。別言語への対応や交換形式は別途必要性を確認する。

## 入力と責務の境界

[`HandSnapshot`](../mahjong-domain-core/MahjongDomain/HandSnapshot.lean)は37種の手元牌と
固定面子を表す。`standing`はツモ牌を含む手元の全牌であり、和了牌を別途渡す場合も
既に`standing`に含まれる牌を指す。和了牌をもう一枚追加して数えない。
固定面子は順序ではなく内容と多重度で扱い、赤5、鳴きの種類、鳴き位置、鳴き元を
保持する。

`HandSnapshot`だけからは和了方法、場風・自風、立直状況、ドラ表示牌、局の本場数などを
得られない。したがって計算APIは牌姿に加えて、それらの計算条件を明示して受け取る。
概念上の入力は次のとおり。

```text
WinInput
  hand        : HandSnapshot
  winningTile : Tile37
  method      : Ron | Tsumo
  context     : WinContext
  rules       : Rules
```

これは概念図であり、実際の言語・型名・引数形式は未確定である。

- `hand`は和了牌を含む和了時点の牌姿とする。通常は`standing.total + 3 * fixedMeldCount = 14`
  を満たす。槓は固定面子1組として数える。牌種ごとの物理枚数上限と固定面子構成も検証する。
- `winningTile`は和了形を完成させた牌種で、`hand.standing`に少なくとも1枚含まれる。
  同種牌が複数ある場合、どの牌姿上の同種牌を指すかという個体IDまでは区別しない。
- `method`はロン／ツモを明示する。ロンでは`winningTile`が他家の捨て牌から加わった牌、
  ツモでは自ら引いた牌を表す。和了方法だけで河や局面の履歴を推測しない。
- `context`は役・符・支払いのうち牌姿以外の事実を保持する。必要な情報が不明な場合、
  事実を補完せず入力不備または判定不能を返す。
- `rules`は役・符・点数・切り上げ・支払いに用いるルール設定であり、結果に含めた
  ルール識別子から再現できるようにする。

`WinContext`の候補項目:

| 情報 | 用途・注意 |
|---|---|
| 場風、自風 | 役牌と符の判定 |
| 親／子 | 支払い計算 |
| 立直、ダブル立直、一発 | 成立した状態を明示。宣言履歴の再生は行わない |
| 海底・河底、嶺上開花、槍槓 | 和了状況に応じた役の判定 |
| 天和・地和等 | 配牌・局開始の事実が必要。牌姿だけから推定しない |
| ドラ表示牌、裏ドラ表示牌 | ドラ数。裏ドラは該当する立直条件も検証する |
| 本場、供託 | 最終支払いの加算。役・符の判定とは区別する |

項目の型と必須性は未確定である。少なくとも「偽」と「不明」を混同しない表現を使い、
裏ドラや一発など成立条件を入力事実と矛盾したまま計算しない。

## `AfterRon`の判断

点数計算のためだけに、段階設計で提案されている`HandPhase`へ`AfterRon`を追加する
必要はない。
ロンとツモの区別は上記の`method`で明示できる。和了は局を終了させるイベントであり、
段階設計でも局の終了は牌姿の段階型の対象外としている。`AfterRon`を段階に加えると、
牌姿の安定段階と終局イベントの責務を混在させるおそれがある。

`HandPhase`を拡張する設計判断が将来必要になった場合は、共有段階型そのものの意味と
複数consumerでの必要性を確認した上で、別途設計する。点数計算側でCoreの段階型を
独自複製したり、`unknown`をロンとして解釈したりしない。

点数計算で重要なのは`AfterRon`というフェーズ名ではなく、和了牌・和了方法・和了時の
牌姿・局面情報が矛盾なく入力されることである。和了牌はロンでもツモでも
`HandSnapshot.standing`に含まれる。ロン牌を足す前の13枚相当の牌姿しかない場合は、
そのまま計算せず、和了牌を含む和了時牌姿へ変換する呼び出し側の責任とする。

## 計算パイプラインと出力

計算は少なくとも次の段階を区別する。

1. **入力検証:** 枚数、固定面子構成、牌種ごとの物理枚数、和了牌の所在、和了方法と
   状況情報の整合性を検査する。不正な入力を成功した0点などに読み替えない。
2. **和了形の分解:** 標準形と特殊形を列挙し、和了牌がどの部分を完成させるかを保持する。
   同じ牌姿に複数の分解・和了牌の受け入れ方がある場合に備える。
3. **役判定:** 各有効な分解と局面条件に対して役を判定する。ドラは役ではなく、役なしの
   手を和了可能にするものとして数えない。
4. **符・翻・役満評価:** 分解ごとに符、役の翻数、ドラ数、役満の種類・重複数を算出し、
   ルールに従い採用する得点候補を決める。
5. **基本点・支払い:** 得点候補、親子、ロン／ツモ、本場、供託を反映し、支払い内訳を返す。

結果型は、最終点だけでなく検算可能な内訳を保持する。

```text
WinResult
  selectedInterpretation
  yaku
  hanBreakdown
  fuBreakdown
  limit
  basePoints
  payments
  rulesId
```

概念上の内訳には、採用した和了形、役ごとの翻数、赤・表・裏ドラ数、符の各加算理由、
切り上げ後の基本点、ロン／ツモの支払い、本場・供託の加算を含める。複数の有効な
和了形がある場合は、適用ルールに基づく採用理由を追跡可能にする。結果の内訳から
合計点と支払いの整合性を検証できることを目標とする。

## ルール設定

ルール差分が変えるのは役・符・上限・支払いのどの規則かを識別し、設定を構造化する。
少なくとも以下は採用値を確定してテスト可能にする。

- 喰いタン、後付け、複合役・役満の扱い
- 数え役満、役満の複合・責任払い
- 切り上げ満貫、満貫未満の切り上げ
- 七対子の符、平和ツモの符などの細則
- 本場・供託の加算とツモ時の分配
- 赤牌の枚数、採用する牌セット

個別大会やプラットフォームのルール差分を一律の「標準」と決めつけない。未指定の
設定に対するデフォルトは、実装前に選択理由と適用範囲を明記する。

## 非目標と依存関係

- 局のイベント列、河、鳴き・立直の合法性、牌山、順序を復元・検証すること。
- シャンテン数、打牌候補、戦略、和了確率を計算すること。
- `HandSnapshot`や`FixedMeld`を点数計算用に再定義すること。
- 入力から欠けている局面事実を推測してスコアを返すこと。

レポジトリはCoreの型を依存として利用する。`HandSnapshot`から和了形へ射影するときも、
手元と固定面子の情報を混同せず、槓の占有枚数と面子数を区別する。赤5の所在や
固定面子の鳴き情報を、34種への正規化後に復元できると仮定しない。言語をまたぐ
交換が必要なら、Coreの交換形式とバージョンを別途定め、言語間の共通テスト例を用意する。

## 実装前の検証例と未決事項

最低限、以下を含む例題と信頼できる期待値を用意し、分解・役・符・支払いの各内訳まで
照合する。

1. ロン／ツモ、親／子、場風・自風、平和・役牌・断么九などの基本ケース。
2. 門前／副露、チー・ポン・各種槓、赤5・ドラ・裏ドラを含むケース。
3. 立直・一発・海底／河底・嶺上開花・槍槓などの局面役と入力条件。
4. 七対子、国士無双、複数の和了形、和了牌の位置によって符・役が変わるケース。
5. 満貫等の境界、役満・複合役満、親子別支払い、本場・供託。
6. 和了牌が`standing`にない、手牌枚数が不整合、5枚目の牌、役なし、必要な局面情報が
   欠落・矛盾する入力の明示的な拒否。

実装に進む前に、採用ルールと設定可能範囲、対象となる役・特殊役満、責任払い、
複数解釈時の採用規則、入力検証の厳密さ、使用言語と交換形式、出力APIを決める。
期待値は独立に検証された資料または既知の実装との照合を記録し、テスト自身を唯一の
根拠にしない。
