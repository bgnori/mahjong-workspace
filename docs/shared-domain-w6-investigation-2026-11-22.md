## 要旨

`SharedDomainW6`は移行の段階名を持つ独立パッケージで、双方の実装に依存する
接続証明を置き、相互依存を避けてきた。共有牌種・面子型を直接使う現在は、
その中に各利用側だけに依存する定理や重複補題も残っている。
**名前を変えるだけでなく、定理の責務ごとに移し、移行用ファイルとしては発展的に解消する**
方向が妥当である。

W6の役割は、共有型への**移行中に両consumerの意味が対応することを確かめる**
ことである。両者に依存する定理を恒久的な公開契約にすることは前提としない。
解消時は検証の役割を確認し、維持すべき仕様・回帰は適切な場所へ引き継いだうえで、
移行のためだけの定理・パッケージは削除できる。

Coreの役割は共通の構造・保証を定義することであり、両consumerの探索・分類や
互いの型に依存する接続をCoreへ移すことではない。特に、**1牌種につき物理牌4枚**
という麻雀の基本ルールはCoreの責務である。consumerでたまたま一致する定数ではなく、
ゲームについての基礎知識として扱う。Leanの`axiom`宣言を導入するという意味ではなく、
共有定義として表し、既存の物理牌表現との整合を証明する。

## 部分形と13枚相当の牌姿

4・7・10枚形は、通常形の13枚相当の牌姿のうち注目する部分として捉える。
残りは鳴きなどで固定された面子、または人が自明に分けて考えられる完成面子として
取り除いたものと考える。小さな形で理解・分類できることは目的であり、13枚形の
大量の計算結果を人に直接扱わせることを前提にしない。1枚単騎も同様に考えられる。
槓は物理的には4枚でも1面子なので、「13枚相当」と物理枚数は区別する。

これは異なる種類の「待ち」を導入する話ではなく、同じ待ちについて、注目部分だけか、
取り除いた牌も含むかという**入力情報の違い**である。取り除いた牌が既に使っている
枚数を忘れれば、部分形の計算結果だけでは元の全体で何枚加えられるか決まらない
場合がある。部分形が全体を代表できる条件は必要に応じて明示する。

分類側の[待ち核を保つ面子除去](../mahjong-wait-classification/Mahjong/WaitDecompositionCode.lean)
は「自明に分離できる」を考える手掛かりになる。ただし、鳴きなどの固定と
待ち核を保つ除去が常に同じ意味だとは未決定であり、片方から他方を仮定しない。

## 現在の証明と責務

| 現在の宣言 | 内容 | 整理の方向 |
|---|---|---|
| `CountsMatch`と`toDomain`・`length_eq`・`draw` | 分類側の牌種リストとShantenのカウントが各牌種で一致し、加牌や総数でも対応する。牌種型の変換ではない。 | 移行中の照合として扱い、既存の`TileCounts.ofList tiles = hand.counts`を直接使えるか検討する。汎用の総数補題は既存Core・Mathlibの定理と照合する。 |
| `flatMapMentsuComponentsTiles` | 分類側の面子構成部品の牌展開に関する補題。 | 分類側には同内容のprivate補題`flatMap_mentsuComponents_tiles`があり、重複を除く。 |
| `standardCompletion_toStandardAgari`、`standardAgari_toDomainCompletion_fixed` | 共有の通常形分解と分類側の和了判定を両方向に接続する。後者は固定面子数・手牌枚数を使って分解面子数を特定する。 | 分類側に対応定理を集約し、両方向を共有仕様に対する契約として整理する。既存の`IsStandardAgari.toDomainStandardCompletion`は面子数の存在を既に示す。面子数を特定する一般的な牌数の帰結も併せて検討する。 |
| `completeTileCount`、`notCompleteAtThirteen`、`handStepTileCount`、`IsFixedContextWait`、`isShapeShanten_zero_iff_exists_fixedContextWait` | 固定文脈の通常形完成・一歩の牌数と、通常形シャンテン0／待ちの存在の関係。分類側への依存はない。 | Shanten側の仕様・証明へ移す候補。単独で成立する証明とその前提を維持する。 |
| `fixedContextWait_iff_classificationWait`、`isShapeShanten_zero_iff_exists_classificationWait` | 同じ手元牌について、固定牌の占有も考慮した待ち・通常形シャンテン0と分類結果の対応を示す。 | 共有ルールと各consumerの仕様への移行中の整合性確認と位置付ける。恒久的な横断公開APIを前提にせず、引継ぎ後の要否を判断する。 |
| `capacityAB`、`capacityB_shanten_zero` | 同一の手元牌姿でも固定牌の占有で待ちが変わる例と、後者の通常形シャンテン0。 | 具体例の意味と回帰保証を引き継ぎ、恒久的に両consumerが依存する試験にするかは決め打ちしない。 |
| `assert_no_sorry` | 横断定理とA/B例の推移的な証明穴不在検査。 | 移行中の検査を維持し、残す定理は移動先でも検査する。 |

Coreの`StandardCompletion`は、指定した面子数の分解証人と牌種カウントの一致を
表し、単独では各牌種4枚以下や固定牌の内容を保証しない。
Shanten側では既に`Complete.mentsuHand_iff_standardCompletion`が
固定文脈の`ValidHand`を別の条件として保持している。
分類側の`IsStandardAgari`も牌列の分解可能性であり、合法な聴牌枚数と候補牌の
枚数制限は`IsWaitFor`の別条件である。これらを一つの完成述語として無条件に
同一視しない。

## 4枚則と占有

以前の議論で「分類側の待ちは固定牌の占有を知らない」と述べたが、これを
「分類側に枚数制限の知識がない」と受け取れる表現は不正確だった。
分類側の`IsWaitFor`は入力牌列について各牌種が4枚以下であることと、待ち牌を
もう1枚加えられることを明示的に要求する。

W6が比較する分類側の入力は**手元牌だけ**で、固定牌の種類・枚数を含まない。
`C(t)`を手元の牌種`t`の枚数、`F(t)`を固定牌の占有枚数とすると、
分類側の候補牌条件は`C(t) < 4`だが、固定文脈での条件は`C(t) + F(t) < 4`である。
いずれも同じ4枚制限を扱うが、数える範囲が異なる。
固定文脈の有効性は、加牌前の全牌種について`C(t) + F(t) ≤ 4`も要求する。
`remainingCapacity = 4 - F(t)`は自然数減算のため、過剰占有の検証の代わりにはならない。

現状、分類側は`copiesPerTile = 4`を持ち、Shantenは4を直接使い、Coreにも
物理牌IDやInt37の容量の表現がある。4枚則をCoreの正本として明示し、これらが
一貫するようにする。牌種ごとのカウントが上限内か、候補牌をもう1枚加えられるかは
共有ルールを使う基本的な判断の候補である。何を数えるか、手牌枚数や固定面子数の
条件はconsumer側の入力・用途に従う。既存の物理IDの一意性と、赤5・通常5を分ける
Int37のスロット別上限も保持する。

W6のA/B例では、分類入力は共通の`111m東`で東待ちとなる。
固定牌が`東東東・123p・123s`なら東は手元1枚と固定3枚の計4枚なので追加できず、
`南南南・123p・123s`なら東は追加できる。すなわち固定牌が入力外にある限り、
分類結果だけからこの差を決めることはできない。

固定牌を含む牌姿を分類する場合は、その牌も枚数判定に反映され得る。しかし現行の
分類器はその牌を固定済みと指定する入力を持たず、分解・面子除去の候補として扱う。
よって、固定牌を連結すれば常にW6と同じ意味になるとはまだ言えない。

分類の[病的構造](../mahjong-wait-classification/README.md)には、牌を除くことで
枚数制限の影響が結果に現れる例もある。ただし病的構造はconsumerの計算結果を
調べる話であり、W6や共有ライブラリの整理に際してその結果を先取りして一般化する
対象とはしない。

## 実施候補と検証条件

1. Coreに1牌種4枚というルールを正本として表し、物理牌とInt37の表現との整合を示す。
   牌種カウントの有効性・加牌可能性の共有基本則を検討し、各consumerが直接利用する。
   過剰占有を見逃す飽和減算や、赤牌スロットの検査省略を避ける。
2. W6のうち分類側だけの通常形和了とCore分解の対応、Shanten側だけの固定文脈と
   通常形シャンテンの関係を、それぞれの仕様に照らして整理する。
   面子数・13枚相当・加牌と交換・通常形という前提を維持し、重複補題を除く。
3. 移行中はW6で両側の対応とA/B例を検証する。完了後は、必要な仕様・回帰が
   引き継がれたことを確認し、移行用の`CountsMatch`や横断定理を含むパッケージの
   要否を判断する。両consumerの相互依存や、横断公開APIの恒久化を前提にしない。
4. `FixedMeld`型そのものの共有は4枚則とは別に判断する。現型は順子・刻子・槓の
   形と占有を保持するが、鳴きの種類や赤牌の同一性は保持しない。
   この整理は`Completion`のconsumer横断統一・改名を先取りしない。

移行時はCore・両consumer・移行中のW6のLeanビルドと`sorry`不在検査を維持し、
待ち集合・分解結果、A/B、固定槓、容量超過など影響範囲の既存回帰を確認する。
公開APIや計算結果を変更する場合は影響範囲とGo契約を別途確認する。
読みやすさの人手確認は機械検証とは別の持ち越し事項である。

## 現時点の検証

本書は既存のコード・テスト・資料と対話を調査した記録であり、新たな定理の証明や
実装変更は行っていない。直前の抽出作業ではCore、Shanten、待ち分類、W6のLeanビルドが
通過している。現在のW6では主要な横断定理とA/B例の`assert_no_sorry`があり、
Shanten CIはCoreと分類側の`main`を取得し、検証した各リビジョンを記録する。
