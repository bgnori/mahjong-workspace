# 共有牌姿表現の設計案

作成日: 2026-11-26

## 目的と位置付け

各リポジトリが同じ意味の牌姿を交換し、完全ハッシュをその牌姿に対して
計算できるようにする。[牌姿キーの計画](./hand-perfect-hash-plan.md)と
議論した案Aを基に、正規化済みの牌姿と固定面子をCoreの共有概念として設計する。
Coreの共有型、hand-hashの入出力、シャンテン向け射影を試作済みである。
交換形式やキーの版固定、全域の証明、他consumerの移行は未完了である。

Coreが牌姿の意味を定義し、各consumerがその使い方を定義する。各リポジトリに
同じ概念の別定義を維持せず、段階移行後はCoreの型を直接利用する。言語を
またぐ場合も、同じ意味と交換契約に従う。キーの番号付けやシャンテン計算などは
Coreの牌姿の定義とは分離する。

## 共有牌姿の構成

概念上の形は次のとおり。実装では固定面子をリストで保持し、
同一性で順列を無視する。

```text
HandSnapshot
  standing   : TileCounts
  fixedMelds : Multiset FixedMeld
```

- `standing`は固定面子に属さない手元牌の、34牌種に正規化したカウント。
  暗槓の4枚も手元側ではなく固定面子側に置く。
- `FixedMeld`は固定面子**1組**の型、`fixedMelds`はその値の**多重集合**であり、
  両者に同じ情報を二重に格納するわけではない。固定面子なしも対象である。
- 多重度は保持するが順序は保持しない。同じ面子が2組あれば2組と数える。
  実装に順序付きリストを使うとしても、牌姿の同一性はリストの順列を区別しない。
- 赤5と通常5、物理牌の個体、手元牌や固定面子の順序、ツモ牌の区別、
  立直などの局面情報は含めない。必要な場合は牌譜や別の情報として保持する。
  詳細な牌譜表現からはこの牌姿へ射影できるが、その逆は一般にできない。

### 既存概念の再利用

[`MahjongDomain.Tile`と`TileCounts`](../mahjong-domain-core/MahjongDomain/Tile.lean)、
[`Shuntsu`、`MentsuCandidate`、`Kan.occupiedTiles`](../mahjong-domain-core/MahjongDomain/Parts.lean)
を正本として使う。同じ順子・刻子・槓占有を表す別型や別名を新設しない。
[`MahjongDomain.Hand`](../mahjong-domain-core/MahjongDomain/Hand.lean)は現在、
手元カウントだけを表す。これを牌姿全体と同一視せず、`HandSnapshot`は
`TileCounts`を直接フィールドに持つ。手元部分の改名は未決定である。

固定面子は面子の形に加えて固定・鳴きの情報を持つため、新たな共有概念として
必要である。次は構成の例であり、同じ情報を別フィールドに重複保持しない。

```text
FixedMeld
  chi       (sequence : Shuntsu) (calledOffset : Fin 3)
  pon       (tile : Tile)        (caller : RelativeCaller)
  daiminkan (tile : Tile)        (caller : RelativeCaller)
  kakan     (tile : Tile)        (caller : RelativeCaller)
  ankan     (tile : Tile)
```

`Shuntsu`はすでにスートと開始位置を持つので、チーにそれらを別途持たせない。
`calledOffset`は既存の`Shuntsu.orderedTiles`における先頭・中央・末尾を表し、
チーの鳴き元は四人麻雀では上家である。ポン・大明槓・加槓の`caller`は
下家・対面・上家の相対位置とし、加槓は元のポンの鳴き元を保持する。
暗槓は鳴き元を持たない。`RelativeCaller`はhand-hash試案にも定義があったが、
実装では[Core](../mahjong-domain-core/MahjongDomain/HandSnapshot.lean)に移し、
hand-hash側の重複定義は取り除いた。

占有牌の展開ではチーに`Shuntsu.tiles`、ポンに
`MentsuCandidate.koutsu`の牌展開、槓に`Kan.occupiedTiles`を再利用する。
`MentsuCandidate`は固定状態を含まない順子・刻子の**形**であり、
`FixedMeld`そのものでも槓でもない。形を使う計算に射影する場合、
チーは`MentsuCandidate.shuntsu`、ポンは`MentsuCandidate.koutsu`へ写せる。
固定状態と鳴き情報はその射影では失われる。槓は`MentsuCandidate`に写さず、
占有牌として別に扱う。

## 妥当性と同一性

共有型を構築できることと、キー対象として有効であることは分ける。
固定面子単体については、たとえば`Shuntsu`と`Fin 3`により不正な順子や
範囲外の鳴き位置を表せないようにする。現状の共有型は牌姿全体の条件を
内包せず、hand-hashはencode時に検証する。検証済み型などの設計は今後の課題とする。
外部データの取り込みは不正値を明示的に拒否する。

鳴き込みキーの対象では、固定面子数を`m`、手元牌数を`h`として：

- `0 ≤ m ≤ 4`、`h + 3m = 13`または`14`。
- 手元牌と全固定面子の占有牌を合算した各牌種の枚数が4以下。
- 槓は1面子だが4枚を占有する。加槓は元のポンに追加する別面子ではない。

これらは構造上の条件であり、特定の牌譜・ルールでの到達可能性を証明しない。
キーの対象を決める13・14枚相当の条件を、より広い用途の共有型そのものに
無条件で課すとは限らない。

共有牌姿の同一性は、手元の各牌種の枚数が一致し、固定面子が種類・内容ごとに
同じ多重度で存在することとする。例えば同じ`123m`のチーでも、1mを鳴いた場合と
3mを鳴いた場合は異なる。大明槓と加槓も異なる。一方、固定面子の並べ替えや
赤5と通常5の違いは区別しない。

## 完全ハッシュとの関係

### 鳴き込みキー

`MeldAwareHandKey`は、有効な共有牌姿の上記の同一性に対するキーとする。
encodeは対象となる共有牌姿を受け取り、decodeは同じ共有牌姿を返す。
往復はリスト順ではなく共有牌姿の同一性について成立させる。
キーの対象外の牌姿や、decode時の範囲外・無効な候補の穴は明示的に拒否する。

現行試案は手元カウントをrankし、固定面子を番号順に並べた重複を許す組として
rankする。`Shuntsu`の利用はチーのスート・開始位置をまとめるものであり、
必要な情報を減らさないため、この方式と両立する。固定面子1組の候補数は
現行仕様では403通りであり、候補空間の上界は符号付き64ビット内である。
ただしこれは実装の全域正当性や速度の証明ではない。
番号付けの詳細、範囲、往復と単射の証明、永続化の版管理は
[キー計画](./hand-perfect-hash-plan.md)の責務とする。

### 牌集合キー

共有牌姿から、手元カウントと各固定面子の占有牌を合算して`TileCounts`を得る。
これを`TileCountsKey`に渡す。この射影は手元／固定面子の区別、面子の形や
鳴き情報を失うため、牌集合キーから元の共有牌姿を復元することはできない。
二つのキーは別の型・別のキー空間として扱う。

## 各consumerとの関係

### シャンテン計算

有効な共有牌姿から、手元カウントと固定面子の形・占有牌を取り出せば、
シャンテン数の計算に必要な情報を得られる。鳴き牌・鳴き元は不要であり、
計算向け射影で失ってよい。現在の
[`Shanten.Capacity.FixedMeld`と`ValidHand`](../mahjong-shanten-calculation/Shanten/Capacity/Basic.lean)
は、形と合算容量を扱う先例である。暗槓も固定面子として渡す。
[`ofHandSnapshot`](../mahjong-shanten-calculation/Shanten/Capacity/HandSnapshot.lean)を
試作し、面子ごとの占有牌と固定面子数、代表的なシャンテン結果を実行例で確認した。
射影自体は妥当性を検査しないため、利用側で容量と枚数を検査する。

逆に、現行の[シャンテンGo入力](../mahjong-shanten-calculation/shanten.go)は
鳴き元とチーの鳴き牌を持たないため、単独では共有牌姿を復元できない。
共有牌姿には赤5情報がないため、Int37入力へ戻す際も元の赤牌の位置は
復元できない。特に通常5のInt37枠の上限は3枚であり、正規化後の5をすべて
通常5として機械的に戻すことはできない。赤牌情報を必要としない計算には
正規化済みの共通表現を受け取る境界を設け、欠落情報を推測しない。
現行Go契約の互換性や変更方法は移行時に別途決める。

### 待ち分類

待ち分類の[`Hand`](../mahjong-wait-classification/Mahjong/Hand.lean)は
手元カウントと、通常形の残り面子数・枚数条件の証拠を持つ。
[`MentsuCandidate`](../mahjong-domain-core/MahjongDomain/Parts.lean)は
手元牌から通常形を分解するときの面子の形であり、共有牌姿の固定面子とは異なる。
共有牌姿から手元部分と残り面子数を渡せるが、現行の分類は通常形の聴牌手牌が対象で、
任意の牌姿や14枚相当の牌姿をそのまま分類できるわけではない。
現行Go APIの対応手牌サイズにも制限がある。

現行の[`IsWaitFor`](../mahjong-wait-classification/Mahjong/WaitCompletionFinder.lean)
は手元牌に対する4枚上限を検査するが、固定面子の占有牌を入力に持たない。
例えば固定面子が`111m`・`234p`・`567p`、手元が`1m222s`の場合、
手元だけの通常形では`1m`を加えると完成するが、固定面子を合わせると5枚目である。
固定面子込みの待ちや分類結果が必要なら、共有牌姿から占有容量を渡す仕様・実装と
検証が別途必要である。待ち候補だけでなく、分解・分類結果への影響も確認し、
単に既存の分類結果を流用できると仮定しない。

## 交換と移行

1. Coreの意味・同一性・占有牌展開を定義し、公開語彙と文書を更新する。
   新規の`FixedMeld`が既存の形の型と意味的に重複しないことを確認する。
2. hand-hashは共有牌姿を直接入力・出力に使う。現行試案の
   `MahjongDomain.FixedMeld`などは同じ名前空間にあるため、Coreへ移す際には
   衝突する二重定義を残さず、移行中の変換と証明も役割・撤去条件を明示する。
3. シャンテン・待ち分類では必要な部分や射影を使い、すべての呼び出しに
   知り得ない鳴き情報を要求しない。既存の同義定義は直接利用へ移行し、
   情報を落とす変換は逆変換可能だと扱わない。
4. 言語間の交換形式について、34牌種の順、固定面子の種類・各フィールド、
   多重度と順序の意味、不正データの扱い、版を明文化する。Leanの
   `TileCounts`は関数なので、その内部表現をそのまま交換形式とはみなさない。
   必要な言語へ同じ意味を移植し、共通例と相互変換の検査を用意する。
   交換形式の版とキー番号付けの版は別々に管理する。

最低限の検証例は、固定面子なし、異なる順序、重複チー、各鳴き牌・鳴き元、
3種類の槓、加槓の元ポンの鳴き元、手元と固定面子の合算4枚超過、
13・14枚相当、および固定面子により5枚目になる待ちを含む。
キーについては例に加え、全有効入力のencode成功・往復・単射と、
decode成功キーの再encodeを証明する。
